3 What would have been simpler as one agent with tools, and why?

Short answer: all three of these tickets, and ticket 101 most of all. Each one is a short, mostly linear checklist over the same 9 MCP tools.

  • Ticket 101 is the clearest case. The useful work was 8 distinct successful tool calls (ticket, stock looked up two ways, vendors, invoices two ways, cash, and preparing #501), plus the tee order the tool refused. The multi-agent version spent 26 model calls and about 89,000 tokens to get there. Most of the overhead was re-explaining the same facts across hand-offs. Each agent starts fresh, so the Boss, then Inventory, then Customer Service each made Accounting re-check cash and #501. One agent holding one context would have read those facts once. Estimate (not run): one agent would need roughly one model call per tool step plus a final answer, about 8–10 calls.
  • Ticket 102 is a three-step chain: read the lease, check cash, prepare rent. The multi-agent run was already efficient (7 calls), so splitting it bought clarity, not savings.
  • Ticket 103 invoked Accounting twice and still left the customer without a reply. One agent working through stock → margin → vendor → cash → reply would not have “forgotten” Customer Service, because there would be no hand-off to skip.

Why the multi-agent design still earned something:

  • Least privilege you can see. Only Accounting can call prepare_payment_request, and no agent can call record_approved_payment. The “Who did what” cards and the audit chain (boss → facilities → accounting) make each decision easy to audit.
  • Focused prompts work. Facilities' claim-by-claim verification on ticket 102 is exactly what its prompt asked for, and it produced the cleanest run.
  • But the safety came from the tools. The open-invoice rule, the insufficient-funds flag, the duplicate-call cache and human approval are all code. A single agent with the same tools and backend gates would have been just as safe.

My verdict: for this shop and these tickets, five agents were more architecture than the work needed. Multi-agent pays off when the domains are bigger than one context window, or need different tools and people. Here it mostly multiplied tokens. If I kept it, I'd pass each specialist the facts already gathered in a shared ticket record, and stop specialists from re-delegating questions that were already answered.
